Setup documentation drift is the silent tax on every new contributor. A repository's README describes the setup as it was written, not as it is: versions move on, services are added, and steps live in tribal knowledge. The person who discovers the gap is the newest team member on their first morning, with nobody to ask. Research from Atlassian DevEx 2025 and Cortex 2024 shows onboarding friction as the top developer-experience pain point and new hires taking over a month to land their third pull request.

HUMBLE treats a repository's setup docs as an executable procedure. It follows the documented steps on a clean Linux machine (a Docker container with no cache, no pre-installed tools, no host leakage) exactly as a newcomer would. The pipeline runs six specialized agents in sequence: Scout reads the docs next to manifests, lockfiles, compose files, CI workflows, and application code to build a fact base; Planner turns prose into the exact ordered shell commands a newcomer would run, flagging where docs and code disagree; Runner executes every step on the clean machine with per-step timeouts (5 minutes for test, 25 minutes for install, 12 minutes for build, 150 seconds for serve); Doctor diagnoses failures — known causes get known fixes from a deterministic rule set; when no rule recognizes the failure, Doctor calls IBM Bob (via the DR.BO custom mode) to read the repository and return a structured fix that changes only documentation, environment templates, compose files, or runtime version files — never application source; Verifier discards the machine and replays the repaired guide from zero on a fresh container, proving every fix works end to end; Scribe writes the minimal README diff, patches .env.example or docker-compose.yml, and emits a Setup Passport with evidence for every change (failure log, root cause, fix applied, replay pass).

The engine ran a rules-only audit across 16 public repositories pinned to exact commits (audit/real-16-v2). Nine of the 14 followable READMEs broke on a clean machine; 22 breaks were found; 11 were fixed and re-verified from zero, yielding 6 VERIFIED, 4 PARTIAL, 4 FAILED, and 2 NO-SETUP-DOCS outcomes. The audit ran with the rules brain only (no Bob calls), using a single Docker image per repo determined from .nvmrc, .python-version, CI, or the current LTS. Replay times ranged from 25 to 90 seconds per repository. The numbers come from the recorded artifacts in audit/real-16-v2/audit.json and the per-repo run directories — every verdict, break count, and replay duration is reproducible from these files.
