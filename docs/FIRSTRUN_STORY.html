Your README, assumed proven.

FirstRun follows a repository's setup guide on a clean machine, the way a new contributor would. When a step breaks, it finds out why, fixes it, and replays the whole guide from zero to prove the fix. Maintainers get a corrected README and a record of every repair.

01 · The problem

"Getting started" is the least tested page in most repositories.

A new contributor's first hour decides whether they stay. It usually goes on a setup guide that worked on the maintainer's laptop two years ago.

Code has tests and CI. The README has neither. It drifts quietly as dependencies, runtimes and services change, and nobody notices, because everyone who could notice already has a working machine. These are the breaks we actually hit:

Runtimebcrypt ^3.0.6 does not build on Node 22; the README never says which Node to use.
PlaceholderMONGODB_URL=YourConnectionString copied as told, and the app crashes on it.
ServiceTests need MongoDB and an SMTP server that the docs never tell you to start.
DriftScripts renamed, Compose v1 commands, a pinned Python the image no longer ships.

02 · The solution

Six stages, one rule: nothing counts as fixed until a clean replay passes.

Pick a stage to see what it does and where it lives in the code.

VERIFIED

Every break was fixed and the repaired guide replayed from zero.

PARTIAL

Some breaks fixed and proven; the rest need a human, with the reason written down.

FAILED

The guide can't reach a running app, and the report says exactly where it stops.

NO-SETUP-DOCS

There is no setup guide to test. FirstRun says so instead of guessing one.

03 · Why this solution

The other options each skip the one step that matters: running the docs.

FirstRunYes, in a clean containerRules, then IBM BobReplay from zeroCI drift guard, passport

Evidence beats advice

Every fix ships with the failing log, the diagnosis and the same step passing. A maintainer can check it in a minute instead of trusting a bot.

Rules first, AI for judgment

About 20 deterministic rules handle the common breaks for free and the same way every time. IBM Bob gets only the failures the rules don't recognise, on a Bobcoin budget.

It fixes the docs, not the machine

The output is the smallest README diff that works for everyone, plus a devcontainer and a CI guard so the fix doesn't rot again.

04 · How IBM Bob is used

Bob is part of the engine and part of how we built it.

Doctor brain

Diagnoses unknown failures

When no rule matches, FirstRun calls Bob Shell headlessly in the read-only FirstRun Doctor mode. Bob reads the repo and names the file and line at fault.

2 real diagnoses on maitraysuthar · 0.35 Bobcoins
Custom modes

Four FirstRun modes

FirstRun, Doctor, Planner and Guide ship in .bob/custom_modes.yaml, each with its own role, rules and file permissions.

Fixed on 26 Sep: Bob Shell 2.x reads ~/.bob/settings/
MCP server

FirstRun inside Bob IDE

Plan, verify, status, evidence, guide and drift are exposed as MCP tools, so Bob IDE can run FirstRun and read its evidence.

05 · The team

Two people and six AI agents from four companies, working as one team.

Pick anyone on the map. Nobody holds work only in their own head: GitHub holds the tasks, Discord the conversation, and the Obsidian vault the memory.

GitHub is the shared state

Every task is an issue with a lane label. One branch per issue, and the other side's agent reviews every PR.

Discord for talk

#firstrun_1 on the Helios server. Each agent has its own bot. Only Arnav and Karmanya give orders.

The vault for memory

An Obsidian vault of status, decisions, lessons and findings. Logging there is now every agent's first priority.

Recovery mode

Usage limits hit without warning. Work idle for 45 minutes can be taken over after saying so in chat. It has been used twice.
